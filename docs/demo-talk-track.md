# Booth Demo Talk Track — Run / Observe / A/B Test

Use this as the driver script for dry runs and booth handoffs. It assumes the
loop demo app (`/`) is on the left side of the screen and the Inngest
dashboard is on the right.

## Positioning

- Event: [EVENT NAME], [DATES], booth [BOOTH #].
- Problem we address: eng teams want to ship agents, fast. Ensuring
  reliability and effectiveness of asynchronous code is a heavy lift,
  especially when models, prompts, and patterns are constantly changing.
- Point of view: engineers should not have to build extra infrastructure to
  know their product works. When durability is defined in code, all the data
  needed to observe and improve it is generated by default at execution.
- Primary tagline: **Unbreakable agents, invisible infra.**
- Secondary pillars: Durability / Observability / A/B Testing / Sandboxes
  (beta).
- The loop is the story: **Run** (primitives + Sandboxes) -> **Observe**
  (Traces, Insights) -> **A/B Test** (Metrics, Variants, Defer).

## Marketing-Safe Status

The loop demo runs a real Inngest function: durable steps, retry/replay,
traces, metadata, and (in cloud mode) real score, experiment, and sandbox
primitives. The LLM, research corpus, and score values are synthetic booth
props.

Safe summary line:

> Durability is defined in code, so the data needed to observe and improve
> agents is generated by default at execution. We are showing that loop:
> run, observe, A/B test.

Sandboxes are in beta. Say "beta" every time. In cloud mode with the beta
enabled for the demo environment, the sandbox beat is real. On the local dev
server, the beat is simulated and the UI labels it honestly; do not present
the simulated beat as a live sandbox.

## Audience Routing

Open with:

> How are you keeping your agents reliable today, while the models and
> prompts keep changing underneath them?

Route by answer:

- Reliability-pain-first (outages, retries, queues): spend the time in Run.
  Arm the failure toggle, show retry/replay in the trace, then show the
  sandbox beat.
- Observability-focused (traces, OTel, dashboards): get to Observe quickly.
  Show the trace, the captured-by-default list, and Insights.
- Evaluation-savvy (braintrust/langsmith/homegrown): get to A/B Test. Scores via
  defer, the model A/B test experiment, and "weeks later" outcome scoring.
- Exec or walk-by: use the 90-second loop and the tagline.

Payoff line:

> Unbreakable agents, invisible infra. Run it durably, observe everything it
> generated, measure it against reality. The loop makes the next run better.

If the visitor shows buying intent, hand off with:

> Patrick is talking with teams at the event about exactly this. Want me to
> get you on his calendar while you are here?

Use the event page calendar for the handoff: [EVENT PAGE URL].

## 90-Second Loop

Use this when someone is walking by or the booth is loud.

1. Open with the problem: "Teams want to ship agents fast. Keeping async
   code reliable while models, prompts, and patterns keep changing is the
   heavy lift."
2. On the Run stage, click `Run research agent` with both toggles on.
3. While it runs: "Steps in code are marked by primitives that tell Inngest
   how and when to execute. The model generated an analysis script, so that
   code runs in an isolated sandbox, not in our process."
4. Point right to Inngest: the competitor API failed once, Inngest retried
   just that boundary, and earlier steps replayed from memoized state.
5. Switch to the Observe stage, click `Open trace`: "We did not add
   observability code. The durability we defined generated this data."
6. Switch to the A/B Test stage, click `Good`: "Product behavior just became
   a score on that run. defer() can do the same weeks later, and the A/B test
   compares models with the same scorers."
7. Close with the payoff line: "Unbreakable agents, invisible infra."

## 2-3 Minute Live Walkthrough

1. Start on the Run stage. Frame the scenario: "This is a competitive
   research agent. It pulls internal context, competitor changelogs, and
   market sources, then writes a brief."
2. Keep `Fail competitor API once` and `Run generated code in a Sandbox`
   armed. Click `Run research agent`.
3. When the failure event appears: "The API returned 503. Inngest retries
   the failed step while successful steps replay from memoized state. The
   customer never knows."
4. Show the sandbox result card: "The model wrote that analysis script, so
   it ran isolated: its own filesystem, destroyed after the step. In
   cloud mode this is the real Sandboxes beta."
5. On the right, open the Inngest trace. Walk steps, inputs/outputs, the
   retried boundary, then `create-analysis-sandbox` and
   `run-generated-analysis`.
6. Switch to Observe. Open the trace link, then `Open Insights`:
   "Everything here was generated by default at execution. The same data
   backs Insights queries; there is no pipeline to wire."
7. Point at the code pane: "This is the whole function. Primitives mark the
   steps. Observability is not added code."
8. Switch to A/B Test. Click `Good`, then `Scores` on the right. "Scores
   attach to the run that did the work."
9. Click `Run model A/B test`, then open the Experiment link. "The same
   scorer measures both models on live data. Every score lands on the
   variant that produced it."
10. Close the loop: "Run, observe, A/B test. The result feeds the next
    run. That is the whole product loop, and the infra was invisible."
11. If the visitor is qualified or comparing stacks, offer the Patrick
    follow-up handoff instead of extending the demo.

## What To Show In Inngest

- Runs list filtered to the demo app, with seeded research history.
- `research-agent` runs from `research/run.requested`.
- The trace: step inputs/outputs, the retried boundary, memoized replay.
- The sandbox steps: `create-analysis-sandbox`, `run-generated-analysis`,
  `destroy-analysis-sandbox` (cloud mode only; local shows the simulated
  single step).
- `research/feedback.recorded` events and attached scores.
- The `research-agent-model-bakeoff` experiment with per-variant scores.
- Insights query over runs and scores (cloud, when configured).

## Claims To Avoid

- Do not say Sandboxes are generally available; they are in beta.
- Do not present the local simulated sandbox beat as a live sandbox. The UI
  labels it "simulated locally"; keep your narration consistent with it.
- Do not imply the demo uses a real LLM or real customer data.
- Do not call the seeded local trend production Insights data.
- Do not claim the final Scores product surface is complete beyond what the
  dashboard actually shows.

## Dry-Run Acceptance

The demo is dry-run ready when:

- Drivers can complete the 90-second loop and the 2-3 minute walkthrough on
  32-inch, 16-inch, and 14-inch layouts without awkward clipping.
- The retry beat, sandbox beat, score beat, and bakeoff beat all land in
  order on the deployed cloud demo.
- The sandbox probe reports `mode: "sandbox"` on the deployed demo, or the
  team has explicitly approved the simulated labeling for the event.
- `npm run demo:preflight` and `npm run demo:smoke` pass against the final
  demo URL, and research history is seeded.
- Lauren/Riley/DevRel agree on the scripts, and 2-3 drivers are signed off.
- A 90-second loop and 2-3 minute contingency recording exist.

## If Something Breaks

- If Inngest has no runs, use `/api/demo/status` and check Cloud event and
  signing keys.
- If the cloud sandbox beat fails (403 access_denied, capacity), flip the
  narrative to the beta caveat and show the trace without the sandbox steps,
  or run locally where the beat is simulated. Never debug sandboxes live at
  the booth.
- If seeding fails, rerun `npm run demo:seed-research-load`.
- If network or Cloud auth is flaky, switch to the contingency recording.
